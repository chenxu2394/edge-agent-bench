# INC-001: Telemetry publisher stops after disk exhaustion

**Type:** Synthetic incident used by EdgeAgentBench  
**Reported symptom:** The telemetry publisher stops sending messages at **14:32 UTC**.  
**Expected root cause:** `DISK_EXHAUSTION` — insufficient writable storage prevents outgoing-message persistence, after which the publisher suspends publishing.

## Scenario

A telemetry publisher normally queues outgoing messages and forwards them through an MQTT connection. Around 14:32 UTC, publication stops and messages begin accumulating in the pending queue.

The agent's task is to distinguish the immediate failure mechanism from alternative explanations, using the two read-only tools rather than guessing from the initial symptom:

- `get_incident_logs({"incidentId":"INC-001"})`
- `get_incident_metrics({"incidentId":"INC-001"})`

The tools expose synthetic records from [`data/incidents.json`](../data/incidents.json). They do not change the publisher, storage, or broker.

## Evidence highlights

| Evidence ID | Observation | Diagnostic significance |
| --- | --- | --- |
| **`L-002`** | Outgoing-message persistence fails with `ENOSPC` (no space left on device), shortly before 14:32 UTC. | **Required log evidence.** Directly identifies a storage write failure. |
| **`M-001`** | Disk usage reaches **99%** at 14:32 UTC. | **Required metric evidence.** Supports the storage-exhaustion diagnosis. |
| `L-003` | The publisher suspends publishing after the persistence failure. | Connects the storage failure to the observed stopped publication. |
| `M-005` | Publish rate drops to zero. | Confirms the reported symptom. |
| `M-004` | The pending queue contains **1,260** telemetry messages. | Shows the backlog resulting from stalled publication. |
| `L-004` | The MQTT broker connection remains healthy. | Makes broker connectivity less likely as the primary cause. |
| `M-002`, `M-003` | CPU and GPU utilization are not unusually high. | Does not support compute saturation as the cause. |

The full synthetic log and metric records, including their exact field names and timestamps, are maintained in [`data/incidents.json`](../data/incidents.json). This page summarizes the diagnostic evidence rather than duplicating the entire fixture.

## Expected investigation

1. Read the logs and metrics with `incidentId: "INC-001"`.
2. Identify the `ENOSPC` persistence failure and the high disk-usage reading.
3. Explain the causal chain: **storage exhaustion → persistence failure → publishing suspended → growing message backlog**.
4. Distinguish the immediate cause from unknown underlying reasons for storage exhaustion (for example, what consumed the storage). The fixture does not establish that deeper cause.
5. Cite at least **`L-002` and `M-001`** in the final diagnosis and state any remaining uncertainty.

The expected answer is **disk exhaustion**, not an MQTT authentication failure or a CPU/GPU bottleneck. Merely observing a zero publish rate or backlog is insufficient to establish the root cause.
