# INC-005: Cross-device deduplication key collision

**Type:** Synthetic incident used by EdgeAgentBench.

**Reported symptom:** Downstream analytics stops accepting telemetry from line-b at 02:20 UTC, while line-a continues updating.

**Expected root cause:** `CROSS_DEVICE_DEDUPLICATION_KEY_COLLISION`.

## Scenario

A telemetry pipeline receives samples from multiple edge devices. Each device maintains its own sequence counter.

A downstream deduplication service originally identifies records using `(device_id, sequence)`.

A new deployment changes the effective idempotency key to `sequence` alone, with a 24-hour deduplication window.

Two devices generate distinct telemetry samples with overlapping sequence numbers. The service accepts line-a records first. It subsequently suppresses line-b records sharing the same numeric sequence.

MQTT delivery and payload validation remain successful.

## Required diagnostic evidence

| Evidence ID | Observation                                             | Diagnostic role                             |
| ----------- | ------------------------------------------------------- | ------------------------------------------- |
| L-041       | New deployment uses `sequence` as the idempotency key   | Establishes the configuration regression    |
| L-043       | line-a-02, sequence 6142, key 6142 is accepted          | Establishes the first accepted identity     |
| L-045       | line-b-07, sequence 6142, key 6142 is suppressed        | Demonstrates cross-device collision         |
| M-050       | Only 120 distinct deduplication keys across 240 records | Quantifies the loss of identity information |

## Supporting evidence

- L-040: Previous key included both device ID and sequence.
- L-042 and L-044: Both devices produced different live samples.
- L-046 and L-047: Another sequence number shows the same behavior.
- M-043: The consumer receives 240 messages per minute.
- M-045: line-a has 120 accepted messages per minute.
- M-046: line-b has zero accepted messages per minute.
- M-047: line-b has 120 deduplication suppressions per minute.
- M-049: All 240 device/sequence pairs are distinct.
- M-051: No publisher replay activity.
- M-053: No downstream sink write errors.

## Expected causal explanation

1. A deployment changes the deduplication identity from a composite key to sequence alone.
2. Different devices legitimately reuse overlapping per-device sequence numbers.
3. The first record for each sequence occupies the corresponding deduplication key.
4. A subsequent record from another device collides with that key.
5. The deduplicator treats a distinct sample as a duplicate.
6. line-b telemetry disappears from downstream processing.

## Alternative explanations

- Broker outage: publishing and receiving counts remain healthy.
- Schema failure: schema validation succeeds.
- Database failure: no sink write errors are reported.
- Genuine retransmissions: records have different device IDs and payload hashes; live sampling is confirmed.
- Disk exhaustion: storage utilization is elevated but writes succeed.
- Clock skew: device clocks are synchronized.

## Remaining uncertainty

The records establish the effective configuration change and the resulting false duplicate suppression. They do not establish why the deployment omitted `device_id`, who approved the change, or whether other device groups are affected.
